# Задержка: методика и результаты

[← На главную](../README.md) · [Сверка с ТЗ](REQUIREMENTS.md)

Ориентиры кейса — 500 мс на выбор сценария и 1,5 с от конца реплики до начала
голосового ответа. PDF прямо относит скорость к дополнительным баллам, а не
к условиям сдачи. Эти ориентиры пока не достигнуты в полном голосовом прогоне.

## Что ускорено

- На новом запросе маршрутизация и извлечение полей независимы: теперь они
  выполняются параллельно. При продолжении активной задачи сохраняется проверка
  контекста. Состояние и действия изменяются последовательно после получения результатов.
- Веб-ответ озвучивается потоковым MP3: сервер отправляет первые фрагменты,
  не дожидаясь завершения синтеза всей записи.
- Объяснение готового выбора и альтернативы запрашиваются в фоне. Этот запрос
  не меняет ID сценариев, не запускает действия и не задерживает отправку ответа.
- В Telegram синтез начинается одновременно с отправкой текста. Убраны отдельный
  запрос индикатора набора и отдельное сообщение с транскриптом: он теперь вместе с ответом.
- Повторная одинаковая озвучка Telegram берётся из ограниченного кеша в памяти.
  Браузер хранит аудио последних десяти реплик сеанса для повторного воспроизведения.

Параллельные независимые запросы и потоковая выдача соответствуют рекомендациям
[OpenAI по снижению задержки](https://developers.openai.com/api/docs/guides/latency-optimization).
Сам `gpt-4o-mini`, температура 0.1 и исходный промпт выбора сценария сохранены.

## Парный замер диалога через API

[Полный отчёт с отдельными измерениями](measurements/latency-dialog.json).

Пять учебных запросов RU/KK, два повторения, каждый запрос в последовательном
и параллельном режиме. Порядок режимов чередуется, каждый разговор начинается
с чистого состояния. Всего 20 диалоговых ходов через настоящий API, без подмен.

| Режим | Количество | Медиана диалога |
|---|---:|---:|
| Последовательные вызовы | 10 | 2566,5 мс |
| Параллельные вызовы | 10 | 1559,5 мс |

Снижение медианы — **39,2%**. Выбранные сценарии совпали во всех десяти парах.
Отдельные параллельные запросы были медленнее последовательных из-за вариативности
внешнего сервиса. Совпадение ID не означает полного совпадения извлечённых полей
или формулировок ответов.

Это **время обработки текста движком**. В него не входят запись, STT, TTS,
доставка аудио, объяснение и воспроизведение. Его нельзя выдавать за голосовую задержку.

Повторить из корня проекта (используется API-квота):

```bash
python src/benchmark.py --runs 2 --output .runtime/latency-benchmark.json
```

Результаты сохраняются в отдельный файл; `predictions.json` не затрагивается.

## Голосовой прогон через браузер

[Трассировка живого прогона](measurements/voice-smoke.json).

Для воспроизводимой проверки создана синтетическая русская запись
«Можно оплатить КАСКО в рассрочку?». Chromium получил её через виртуальный микрофон;
MediaRecorder записал WebM, настоящий OpenAI API выполнил STT, маршрутизацию
и TTS, браузер начал воспроизведение. Это проверка всей программной цепочки,
без физических микрофона и динамика ноутбука.

| Измерение | Результат |
|---|---:|
| STT | 770 мс |
| Извлечение полей | 1602 мс |
| Маршрутизатор | 733 мс |
| Формулировка ответа | 770 мс |
| Диалог целиком | 2372 мс |
| TTS до первого фрагмента | 923 мс |
| Синтез всего ответа | 1639 мс |
| Фоновое объяснение | 1088 мс |
| Нажатие «Стоп» → `playing` | 4372 мс |
| Оценённый конец речи → `playing` | **5190 мс** |

Сценарий — `SC31`, объяснение загружено, ошибок JavaScript нет. Значения относятся
к **одной** реплике, а не к медиане на наборе жюри. Этапы перекрываются во времени,
поэтому складывать все строки таблицы нельзя. Задержка после конца речи включает
паузу до нажатия «Стоп», обработку, сеть и буферизацию плеера.

## Что показывает интерфейс

- `router`, `triage`, `response`, `dialog`, `stt` — интервалы серверных операций
  по монотонным часам. Ноль означает отсутствие вызова или длительность менее 0,5 мс.
- `tts_first_chunk` — время до получения первого блока MP3 (до 1024 байт);
  это ещё не момент, когда пользователь услышал звук.
- `tts` — получение всего потока; обновляется отдельно после завершения передачи.
- `explanation` — фоновый запрос объяснения, вне основного пути голосового ответа.
- `client_latency_ms` — интервалы, измеренные самим браузером.
  `speech_to_playback_estimate` начинается с последнего превышения порога энергии
  микрофона, заканчивается первым событием `playing`. Это приближение к концу речи:
  шум, тишина внутри фразы и работа вкладки могут влиять на оценку.
- `stop_to_playback` начинается при остановке записи; `request_to_playback` —
  перед отправкой запроса. Эти показатели отделены от оценки конца речи.
- `latency_ms.total` в браузере повторяет `speech_to_playback_estimate`.
  Пока реального клиентского измерения нет, значение `null`, не ноль.

Медиана в панели включает только голосовые реплики с обнаруженной активностью
и автоматическим воспроизведением. Текстовые запросы, тишина и ручное нажатие ▶
в медиану не входят. «Новый разговор» сбрасывает серию. Скачиваемый JSON содержит
клиентские измерения; серверный `/api/trace/...` сам по себе их не знает.
В Telegram `total_processing` — обработка и отправка; времени первого звука
на телефоне Telegram API не предоставляет, поэтому `total` остаётся `null`.

## Проверка перед выступлением

1. Запустите `python src/web_demo.py`, откройте `http://localhost:8000`.
2. Разрешите микрофон и звук. Проверьте громкость на устройстве жюри.
3. Начните новый разговор и произнесите несколько разных запросов, включая RU/KK
   и смену темы. Нажимайте «Стоп» сразу после фразы.
4. Сравните показания с секундомером: конец речи → начало слышимого ответа.
5. Сохраните JSON реплик и укажите размер серии. Не заменяйте задержку всего
   разговора скоростью приветствия, кешированной записи или одного LLM-запроса.
